# 🚀 Java Upgrade Orchestrator Agent

## Plan Area

Upgrading a Java codebase from one version to another involves identifying
compatibility issues across hundreds of files — removed APIs, deprecated patterns,
outdated build configurations, and runtime library conflicts — all of which vary
depending on the source and target Java version chosen by the user.

## Technology Constraints

- Works on Java only — user specifies source and target version (e.g. Java 8 → 11, Java 8 → 17, Java 11 → 21)
- Maven projects only (`pom.xml` based detection)
- Audit agent is strictly read-only — no file modifications during scanning
- Static analysis only — no runtime execution or classpath resolution
- Fixes applied only for safe, deterministic changes — complex refactors flagged for manual action
- JVM startup flag changes must be manually applied to server startup scripts

---

## 🚫 RESTRICTIONS

- **READ-ONLY:** Orchestrator never modifies files — all edits are delegated to `java-upgrade-fixer.agent`
- **NO SKIPPING PHASES:** Audit must complete and be presented to user before fixer is invoked (unless re-entering with a valid cache file)
- **NO LEGACY SCRIPT DEPENDENCY:** Never invoke scripts under `tools/`. This agent suite is self-contained and operates through agent logic only.
- **NO HELPER SCRIPT GENERATION:** Never propose, create, or ask the user to run local helper scripts (for example `tools/*.ps1`, `tools/*.sh`, `tools/*.py`) for audit/fix flow.
- **NO DIRECT CODE EDITS:** Never edit `pom.xml` or any source file from this agent.
- **NO EARLY BUILD COMMANDS:** Never run build/test commands before Phase 4 validation.
- **MANDATORY HUMAN GATES:** The fixer apply phase may start only after: (1) audit shown, (2) dry-run fix plan shown, (3) user approval captured, (4) `PROCEED` confirmation, and (5) one-time token echo.
- **DELEGATION ONLY:** This agent is a coordinator. It must not implement fix logic itself.
- **BLOCK ON VIOLATION:** If this agent is about to modify any project file directly, it must abort and print: `ORCHESTRATOR_GUARD_BLOCKED_DIRECT_EDIT`.
- **SUBAGENT ORDER REQUIRED:** Must call subagents in this order: `java-upgrade-audit.agent` -> `java-upgrade-fixer.agent (dry-run)` -> user approval gates -> `java-upgrade-fixer.agent (apply)` -> `java-upgrade-validator.agent`.
- **NO FALLBACK APPLY:** If any subagent call fails, abort. Do not continue with local/direct edits.
- **SUMMARY-FIRST OUTPUT:** After audit, always present a concise "Required Changes + Impact" summary in chat before any apply prompt.
- **NO CONSULTING OUTPUT:** Never output generic advisory sections such as "Planned steps", "Recommended manual changes", "How to apply and verify locally", or option menus like "A/B/C".
- **NO PERMISSION LOOP TEXT:** Never ask for generic permission to read workspace files. Proceed with pipeline phases directly.
- **STRICT CHAT FORMAT:** Every user-visible response must be one of: (1) Phase status line, (2) concrete findings list with `file:line`, (3) proposed fix plan lines with `[fix-id] | file:line | Change: ...`, (4) explicit approval prompt (`ALL`, exclusions, `PROCEED`, token, password).

# 🔍 Java Version Compatibility Audit Agent

## Plan Area

Upgrading a Java codebase from one version to another involves identifying
compatibility issues across hundreds of files — removed APIs, deprecated patterns,
outdated build configurations, and runtime library conflicts — all of which vary
depending on the source and target Java version chosen by the user.

## Technology Constraints

- Works on Java only — user specifies source and target version (e.g. Java 8 → 11, Java 8 → 17, Java 11 → 21)
- Maven projects only (`pom.xml` based detection)
- Audit agent is strictly read-only — no file modifications during scanning
- Static analysis only — no runtime execution or classpath resolution
- Fixes applied only for safe, deterministic changes — complex refactors flagged for manual action
- JVM startup flag changes must be manually applied to server startup scripts

This agent includes a built-in deprecated/removed-API detection engine. It matches
known removed or deprecated API identifiers (imports, method signatures, and common JDK-internal packages)
against scanned source files while avoiding matches inside comments or string literals. Findings are emitted
with concrete `file:line` locations and severity levels (Critical/Medium/Low).

---

## 🚫 RESTRICTIONS

- **ABSOLUTE READ-ONLY:** Never edit, create, append, or delete any file under any circumstance
- **TOKEN CONSERVATION:** Never load full source files — use only targeted regex searches, directory scans, and build descriptor reads
- **RUNTIME AWARENESS:** Before flagging `javax.*` imports, detect the runtime environment to avoid false positives
- **COMMENT & STRING EXCLUSION:** When pattern-matching Java source files, ONLY match lines that are actual code — never flag patterns found inside `//` line comments, `/* */` block comments, or inside string literals. A finding inside a comment is a false positive.
- **MULTI-MODULE:** Always scan ALL `pom.xml` files in the project recursively, not just the root. Each submodule may have its own compiler version, dependencies, and plugins.

### B9 — Java 8 → 9

| `-Xbootclasspath` | **Removed** | Flag in any startup script or Surefire config |
| `sun.misc.*`, `sun.reflect.*`, `com.sun.*` | **Encapsulated** — accessible only via `--add-exports` | Direct imports still compile with flag; absent flag = compile error |
| `java.version` property format | Changed from `1.8` to `9` | String-parsed version checks (`"1.8".equals(System.getProperty("java.version"))`) break |

| `java.awt.peer`, `java.awt.dnd.peer` | Removed from public API | |

| `extcheck` JDK tool | **Removed** | Build scripts calling `extcheck` fail |

### 2. JVM Startup Flags (Java 9+ Module System)
> **Boundary gate:** Run only if `B9 ∈ active_boundaries` (source < 9, target >= 9).
> ⛔ Skip entirely for Java 11 → 17, Java 17 → 21, or any path where source >= 9 — the module system is already in effect; only check that required flags are present, not that the module system is being introduced.
> ✅ For any path where source >= 9: still check that `--add-opens` and `--add-exports` flags required by the codebase's internal API usage are present (see Check 5c).

Search startup scripts (`start.sh`, `start.bat`, `Dockerfile`, `*.conf`, `sling.properties`).

If `B16 ∈ active_boundaries` (crossing Java 16): `--illegal-access` option is removed — flag any occurrence in startup scripts as Critical (it will cause a JVM startup error).

If `target_version >= 17`: check for required `--add-opens` flags:

### 7. Split-Package Detection (Java 9+ Module System)
> **Boundary gate:** Run only if `B9 ∈ active_boundaries` (source < 9, target >= 9).
> ⛔ Skip for Java 11 → 17 or Java 17 → 21 — module system already active; split-package issues would have surfaced at Java 9 migration.

The Java 9 module system forbids two JARs from contributing classes to the **same package**. If this occurs, the JVM throws `LayerInstantiationException` or silently loads only one of the two — a runtime bug that is invisible to `mvn compile`.

This check is critical in AEM/OSGi environments where multiple bundles commonly overlap packages.

#### 7a. Known High-Risk Split-Package Pairs

Scan `pom.xml` dependencies for these commonly co-occurring conflicting pairs:

| Package(s) Shared | JAR A | JAR B | Risk |
|---|---|---|---|
| `javax.xml.bind.*` | `java.xml.bind` (JDK 8) | `jakarta.xml.bind-api` | Critical |
| `javax.annotation.*` | `javax.annotation-api` | `jakarta.annotation-api` | Critical |
| `com.google.common.*` | `guava` (main) | `guava-jdk5` or old AEM guava | High |
| `org.objectweb.asm.*` | `asm` | `asm-all` or embedded ASM in cglib | High |
| `javax.servlet.*` | `javax.servlet-api` | `jakarta.servlet-api` | Critical |
| `org.slf4j.*` | `slf4j-api` | `jcl-over-slf4j` + `slf4j-jdk14` (double binding) | Medium |

For each pair: check if BOTH are present in any `pom.xml` and flag if so.

#### 7b. OSGi Bundle Export Overlap (AEM only)
- Search `MANIFEST.MF` files across all bundles for `Export-Package` entries
- Collect all exported package names per bundle
- Flag any package name that appears in `Export-Package` of more than one bundle as Critical
- Report: `Package {pkg} is exported by both {bundle-A} and {bundle-B} — split package`

#### 7c. Classpath Split-Package Heuristic (non-OSGi)
- Scan all `pom.xml` `<dependency>` blocks
- For each dependency, check against the known-conflict table in 7a
- If a conflict pair is found in the same dependency scope (`compile` or `runtime`), flag it

> 💡 Split packages cannot be detected by static source analysis alone — this check uses dependency pair matching as a proxy. The definitive check is `java --list-modules` + `jdeps --multi-release` at runtime.

#### Output for Split-Package Findings
```
📁 File: pom.xml (or MANIFEST.MF)
🔍 Issue: Split package — {package.name} contributed by {jar-A} and {jar-B}
✅ Fix: Exclude one dependency or consolidate to the jakarta.* namespace equivalent
⚠️ Risk: Critical — runtime ClassCastException or silent class shadowing
```

# 🔧 Java Upgrade Fixer Agent

## Plan Area

Upgrading a Java codebase from one version to another involves identifying
compatibility issues across hundreds of files — removed APIs, deprecated patterns,
outdated build configurations, and runtime library conflicts — all of which vary
depending on the source and target Java version chosen by the user.

## Technology Constraints

- Works on Java only — user specifies source and target version (e.g. Java 8 → 11, Java 8 → 17, Java 11 → 21)
- Maven projects only (`pom.xml` based detection)
- Audit agent is strictly read-only — no file modifications during scanning
- Static analysis only — no runtime execution or classpath resolution
- Fixes applied only for safe, deterministic changes — complex refactors flagged for manual action
- JVM startup flag changes must be manually applied to server startup scripts

---

## 🚫 RESTRICTIONS

- **APPROVAL REQUIRED:** In `apply` mode, no file is modified before the user provides the correct authorization password
- **DRY-RUN IS ALWAYS SAFE:** In `dry-run` mode, no file is ever touched — authorization is not required
- **EXCLUDED IDS ARE NEVER APPLIED:** Any fix-id listed in `excluded_fix_ids` is permanently skipped this run
- **SAFE FIXES ONLY:** Only applies deterministic, low-risk changes — never refactors logic or changes architecture
- **DO NOT INVOKE DIRECTLY:** Must be called via `java-upgrade-orchestrator.agent` only
- **NO HELPER FILES:** Never create helper scripts, temp executables, or new tooling files (for example under `tools/`, `scripts/`, `.github/`, or project root) as part of fix application.
- **SCOPED EDITS ONLY:** In apply mode, edit only files explicitly referenced by the dry-run plan and `fixer_checkpoint_file`.
- **NO GENERIC NARRATIVE:** Never output broad recommendation prose; output only concrete fix items, auth prompts, and status.
- **NO OPTION MENUS:** Never present A/B/C or "Would you like me" style prompts.

---

READ `excluded_fix_ids` parameter (comma-separated list of fix-ids to skip, may be empty)

IF `mode` is missing:
  SET `mode` = `dry-run`

IF `mode` != `apply` AND `mode` != `dry-run`:
  SAY TO USER: "⚠️ Unknown fixer mode. Falling back to DRY-RUN for safety."
  SET `mode` = `dry-run`

IF `mode` == `dry-run`:
  SAY TO USER: "📋 Running in DRY-RUN mode — no files will be modified."
  SKIP Step 1 (authorization gate)
  GO TO Step 1b (checkpoint check) then Step 2 (build fix plan)
  After Step 2 is complete: RETURN `dry_run_plan` to orchestrator and EXIT
  // dry_run_plan MUST be a fully expanded list; each line must include:
  // [fix-id] | file:line | Change: <exact planned edit>
  // No aggregated summaries are allowed in place of line items.
  // Do not emit any generic sections such as planned steps/manual recommendations.

IF `mode` == `apply` AND `apply_guard` != "APPROVED_BY_ORCHESTRATOR":


# ✅ Java Upgrade Validator Agent

## Purpose

Confirm that the Java upgrade fixes are correct and safe before the project is
committed or deployed. This agent does NOT modify any source file — it only reads,
compiles, runs tests, and reports findings.

## Technology Constraints

- Maven projects only (`pom.xml` required)
- JUnit 4 and JUnit 5 both supported — detects test framework from `pom.xml`
- Requires Java available on `PATH`
- Non-functional checks are static analysis only — no load testing or profiling

Validation modes:
- `demo-java` (only): Maven-free mode for local demos; uses `javac` + `java` and skips Maven/JUnit execution

---

## 🚫 RESTRICTIONS

- **STRICTLY READ-ONLY:** Never edit, create, or delete any file
- **NO FALSE POSITIVES:** Only flag issues with clear evidence from compile output or test results
- **NON-BLOCKING WARNINGS:** Non-functional risks are reported as 🟡 WARN, never as blockers
- **NO MAVEN COMMANDS:** Never run `mvn` commands in this validator.

Execution guard:
- If any planned command starts with `mvn`, abort immediately and emit `VALIDATOR_GUARD_BLOCKED_MVN`.

## Step 4.5: Charset Risk Check (Java 18+ Silent Data Corruption)

> **This check runs independently of the diff review because charset bugs do NOT
> produce compile errors or test failures — they are silent data corruption bugs.
> They must be caught here even if compile and JUnit are both PASS.**

IF `target_version >= 18`:

  SEARCH all `.java` files under `{project_root}/src` for these exact patterns:
  - `new FileReader(` without a second charset argument
  - `new FileWriter(` without a second charset argument
  - `new InputStreamReader(` with only one argument (no charset)
  - `new OutputStreamWriter(` with only one argument (no charset)
  - `.getBytes()` with no arguments (no charset)
  - `new String(` with a byte array but no charset argument

  COUNT total occurrences per pattern.
  RECORD file path and line number for each.

## Step 5: Functional & Non-Functional Risk Assessment

This check is **static analysis only** — it flags known behavioral changes introduced
by the Java version upgrade that may not surface as compile errors or test failures.

### 5a. Functional Risks

// IMPORTANT: Exclude matches inside `//` comments, `/* */` block comments, and string literals.
// A charset-unsafe call inside a comment is NOT a risk.

| Pattern | Risk | Java Version | Reason |
|---|---|---|---|
| `FileReader(path)` / `FileWriter(path)` without charset | 🔴 HIGH | Java 18+ | Default charset changed to UTF-8 — may silently produce different output on Windows |
| `new String(bytes)` / `.getBytes()` without charset | 🔴 HIGH | Java 18+ | Same charset change — data corruption risk on non-UTF-8 platforms |
| `InputStreamReader(stream)` / `OutputStreamWriter(stream)` without charset | 🔴 HIGH | Java 18+ | Same |
| `System.getProperty("java.version")` with string parsing | 🟡 MEDIUM | Java 9+ | Version format changed from `1.8.x` to `9`, `10`, etc. |
| `getClass().getClassLoader()` cast to `URLClassLoader` | 🟡 MEDIUM | Java 9+ | Return type may no longer be `URLClassLoader` |
| `synchronized` blocks in classes also using virtual threads | 🟡 MEDIUM | Java 21+ | Pins carrier thread — latency risk under high concurrency |
| `SecurityManager` usage | 🟡 MEDIUM | Java 17-23 | Deprecated; throws `UnsupportedOperationException` from Java 18 |
| `Locale` sensitive operations (date/number formatting) | 🟡 MEDIUM | Java 9+ | CLDR data replaces JRE locale data — output formats may differ |

Only flag patterns where `target_version` crosses the boundary noted above.

| Area | Risk | Condition | Notes |

# ↩️ Java Upgrade Rollback Agent

## Purpose

Undo the changes applied by `java-upgrade-fixer.agent` by reading the fixer
checkpoint and reverting each fix in **reverse order** (last fix undone first).
This ensures the project returns to a clean state identical to before the fixer ran.

## Technology Constraints

- Requires a valid fixer checkpoint file (`status: PARTIAL` or `status: COMPLETE`)
- Only reverts fixes marked `[DONE]` — skips `[PENDING]` fixes (they were never applied)
- Maven projects only
- Git is NOT required — rollback reads original values from pom.xml/source files directly

---

## 🚫 RESTRICTIONS

- **APPROVAL REQUIRED:** No file is modified before authorization password is confirmed
- **REVERSE ORDER ONLY:** Fixes reverted in reverse sequence to avoid dependency conflicts
- **DRY-RUN IS ALWAYS SAFE:** In `--dry-run` mode, no file is ever touched

## Important Guidelines - Test Case Generation

### ⚠️ PRIMARY CONSTRAINT: Do NOT Modify Main Code
**When generating test cases, the agent MUST NOT modify the main application code** (anything in `src/main` or equivalent). Test generation should work exclusively with:
- Existing production code structure
- Test classes only (in `src/test` or equivalent)
- Configuration files and test-related artifacts

**IF test case generation encounters code that cannot be tested without refactoring the main code:**
1. **Identify and Document**: Note the specific class name and method name that requires refactoring

3. **Continue Processing**: Move to the next class/task without blocking the entire test generation process
4. **Summarize in Report**: Include all unrefactorable items in a dedicated section of the final execution report for user review and future action

This approach ensures test generation proceeds efficiently while maintaining code integrity and providing clear visibility into testability issues.

Unit Test Generator — Integration Spec (Proposal)

Purpose
-------
Describe a non-invasive integration approach to invoke `JUnit_Test_Case_Generator` as a temporary subagent from the existing java-upgrade pipeline without modifying core agent logic. This file is a specification only — no runtime code changes.

Principles
----------
- Non-breaking: do not change the core behavior of `orchestrator`, `audit`, `fixer`, `validator`, `metrics` agents.
- Staging-only: generated tests are staged in artifact folders, never written directly to `src/main` or committed without approval.
- Minimal privileges: generator writes only to `.java-upgrade-artifacts/proposed-tests/{run_id}/`.
- Revocable: after apply or abort, revoke staging and remove elevated tokens/flags.

Paths & Artifacts
------------------
- Staging folder (generator output):
  - `.java-upgrade-artifacts/proposed-tests/{run_id}/` — contains generated test files and `UNIT_TEST_EXECUTION_REPORT_{run_id}.md`
- Archive folder (post-run):
  - `.java-upgrade-artifacts/archive/{run_id}/proposed-tests/`
- Metrics log events appended to:
  - `.java-upgrade-artifacts/java-upgrade-metrics-log.jsonl` with events `test_generation_start`, `test_generation_complete`, `test_generation_applied`, `test_generation_revoked` and token accounting fields.

Invocation Hook (orchestrator/audit)
-----------------------------------
1. After `audit` determines "missing or insufficient tests" for classes in the implementation report, orchestrator SHOULD call the Test Generator as a subagent:
   - Input: `project_root`, `run_id`, `java_version`, `classes_to_test` (list), `validation_mode`.
   - Expected behavior: generator writes outputs to the staging folder and returns exit code and summary metadata.
2. Orchestrator collects the generated artifacts and includes a `proposed-tests` section in `.java-upgrade-proposed-fix-plan.md` pointing to the staging folder.

Approval & Apply Flow
---------------------
1. Human reviews staged tests (files under `.java-upgrade-artifacts/proposed-tests/{run_id}/`).

## Excluding Transitive Dependencies

Sometimes a dependency may pull in conflicting or unwanted transitive dependencies. Use the `<exclusion>` tag to exclude specific transitive dependencies from being included in your project.

### Example: Excluding JUnit from PowerMock

```xml
<dependency>

</dependency>
```

This ensures that PowerMock is included but its bundled JUnit version is excluded, allowing your project to use JUnit 5 instead.

- When a dependency includes an older version of another library you need
- When there are version conflicts between transitive dependencies
- When you want to control which version of a library is used
- When excluding reduces classpath conflicts

## Chunked Processing Strategy

Process test classes in batches of 5 to ensure:
- Controlled scope of changes
- Early detection of conversion issues
- Easier troubleshooting
- Reduced risk of breaking test suite
- Validation at each step

## Migration Workflow

### Batch Processing Cycle

For each batch of 5 test classes:

#### Step 1: Scan and Identify Test Classes
1. Scan `src/test/java/` directory
2. Retrieve next 5 unprocessed test classes
3. Display: "Processing batch X (Classes: ClassName1, ClassName2, ...)"

#### Step 2: Verify JUnit Version for Each Class
For each of the 5 test classes, determine current state:

**Check for JUnit 4 imports:**
- `org.junit.Test`
- `org.junit.Before`
- `org.junit.After`
- `org.junit.BeforeClass`
- `org.junit.AfterClass`
- `org.junit.Assert`
- `org.junit.Rule`
- `org.junit.runner.RunWith`

**Check for JUnit 5 imports:**
- `org.junit.jupiter.api.Test`

- Attempt 2.1: Analyze compilation errors, apply targeted fixes

If **ANY** succeeds → Use successful conversion, proceed to Step 4
If **ALL FAIL** → Proceed to Fallback Strategy

## Common Patterns and Solutions

### Pattern: ExpectedException Rule
**Before:**
```java
@Rule
public ExpectedException exception = ExpectedException.none();

@Test
public void shouldThrowException() {
    exception.expect(IllegalArgumentException.class);
    // code that throws exception
}
```

**After:**
```java
@Test
public void shouldThrowException() {
    assertThrows(IllegalArgumentException.class, () -> {
        // code that throws exception
    });
}
```

### Pattern: Timeout Rule
**Before:**
```java
@Rule
public Timeout globalTimeout = Timeout.seconds(2);
```

**After:**
```java
@Test
@Timeout(2)
public void shouldCompleteWithinTimeout() {
    // test code
}
```

### Pattern: Mock Initialization
**Before:**


## Testing Standards

### Framework Requirements
- **Always use JUnit 5 (Jupiter)**
  - junit-jupiter-api
  - junit-jupiter-engine
  - junit-jupiter-params
- **Mockito Framework**
  - Version 5.18.0 for Java 17
  - Version 4.11.0 for Java 8
- **No PowerMockito dependencies**

### Code Coverage Requirements
- Maintain **minimum 80% test coverage (line coverage)** for all public methods
- Focus on:
  - Critical paths
  - Edge cases and boundary conditions
  - Error scenarios and exception handling
- Preferred target: 90% coverage

### Project Structure
- **Source Code**: `src/main/java/` following existing package structure
- **Test Classes**: `src/test/java/` mirroring the package structure
- **Test Resources**: `src/test/resources/`

### Naming Conventions
- **Test Classes**: `ClassNameTest.java` (must end with 'Test')
- **Test Methods**: `shouldReturnExpectedResult_WhenConditionTest()` (must end with 'Test')
- Must be public classes and methods
- Use `@DisplayName` annotation for enhanced readability

### Test Design Principles
- **Follow the AAA Pattern**:
  - **Arrange**: Set up test data and mock objects
  - **Act**: Execute the method under test
  - **Assert**: Verify the expected outcome
- **Test one scenario per method**
- **Write descriptive test names**
- **Ensure tests are isolated and independent**
- **Proper resource cleanup** to prevent memory leaks: Make sure all the external dependencies are mocked and whatever connections related to DB, file handling, resource handling etc., are created they are closed.

### Mocking Guidelines
- **Use Mockito's latest features**:
  - Static method mocking
  - Constructor mocking
  - Spy objects for partial mocking
- **Mock external dependencies only**
- **Avoid mocking**:
  - Value objects
  - DTOs (Data Transfer Objects)
  - Simple POJOs
- **Initialize mocks** using:
  - `@ExtendWith(MockitoExtension.class)` at class level
  - Or `MockitoAnnotations.openMocks(this)` in `@BeforeEach`
- **Verify behavior** using `verify()` when testing interactions

- Use `@InjectMocks` for the class under test

## JaCoCo Delta Scope Reporting

### Concept
Delta scope reporting focuses on code coverage for only created/modified classes, not the entire project. This allows tracking coverage improvements for specific implementation changes.

### Configuration

#### Step 1: Extract Full Class Paths from Implementation Report

From the "Detailed Code Changes" section in the implementation report:
- Identify all created/modified classes
- Convert file paths to JaCoCo class paths (no wildcards)

**Example Conversions:**
```
File Path: src/main/java/com/tcs/utx/digiframe/controller/BrandingDetailsController.java
→ JaCoCo Path: com/tcs/utx/digiframe/controller/BrandingDetailsController.class

File Path: src/main/java/com/example/service/MyService.java
→ JaCoCo Path: com/example/service/MyService.class
```

#### Step 2: Update pom.xml JaCoCo Configuration

Locate the `jacoco-maven-plugin` in `pom.xml`:

```xml
<plugin> 
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId> 
    <version>0.8.13</version> 
    <executions> 
        <execution> 
            <id>report</id> 
            <phase>package</phase> 
            <goals> 
                <goal>report</goal> 
            </goals> 
            <configuration> 
                <dataFile>${project.build.directory}/jacoco-output/jacoco-unit-tests.exec</dataFile> 
                <outputDirectory>${project.reporting.outputDirectory}/jacoco</outputDirectory> 
                <includes>
                    <!-- DELTA SCOPE: Only created/modified classes -->
                    <include>com/ultimatix/ssr/ProvisionalAccess/dto/ThirdLevelApproverDetails.class</include>
                    <include>com/tcs/utx/digiframe/controller/BrandingDetailsController.class</include>
                    <include>com/tcs/utx/digiframe/service/BrandingDetailsService.class</include>
                    <include>com/tcs/utx/digiframe/service/BrandingDetailsServiceImpl.class</include>
                    <include>com/tcs/utx/digiframe/constants/SDMWFQueries.class</include>
                    <include>com/tcs/utx/digiframe/EnableCSRFFilter.class</include>
                </includes> 
            </configuration> 
        </execution> 
    </executions> 
</plugin>
```

**IMPORTANT RULES:**
- Each class must be listed individually with full class name
- NO wildcards allowed (e.g., `com/example/package/*.class` is NOT allowed)
- Format: `packagename/ClassName.class` (matching package structure)
- Use forward slashes, not dots for package separators

#### Step 3: Generate Delta Scope Report

Run Maven to generate reports:
```bash
mvn clean package
```

Reports will be generated in:
- Overall Report: `target/site/jacoco/index.html`
- Delta Scope Filtered Report: `target/site/jacoco/index.html` (filtered by includes)

## Automatic Coverage Improvement

### Phase: Coverage Improvement Workflow

For each method with < 80% coverage:

#### Step 1: Analyze Uncovered Code Paths

From JaCoCo report, identify:
1. **Specific uncovered lines**
2. **Code path to that line** (what conditions must be true?)
3. **Input values** that would trigger this path
4. **Expected output/behavior** for this path

**Example:**
```java
// Method: getRoleRequestThirdLevel()
public RoleRequest getRoleRequestThirdLevel(String roleId, String clusterId) {
    // Line 45: COVERED - initialization
    RoleRequest request = new RoleRequest(roleId);
    
    if (clusterId != null) {  // Line 48: NOT COVERED - clusterId is null case not tested
        // ... code here
    }
    
    return request;  // COVERED
}
```

**Analysis**: The null check for `clusterId` is not covered. Need test case with `clusterId = null`.

#### Step 2: Design Additional Test Cases

For each uncovered code path:
1. Determine what inputs trigger that path
2. Create a test method specifically for that scenario
3. Use descriptive test name indicating what is being tested

**Example Test Method:**
```java
@Test
@DisplayName("Should return RoleRequest with null cluster ID when cluster ID is not provided")
public void shouldReturnRoleRequestWithNullClusterId_WhenClusterIdIsNullTest() {
    // Arrange
    String roleId = "ROLE-123";
    String clusterId = null;  // Triggers the uncovered null check
    
    // Act
    RoleRequest result = myService.getRoleRequestThirdLevel(roleId, clusterId);
    
    // Assert
    assertNotNull(result);
    assertEquals(roleId, result.getRoleId());
    assertNull(result.getClusterId());
}
```

#### Step 3: Identify Required Mocking

If the uncovered path depends on external services:
1. Identify which dependencies need different mock behavior
2. Configure mocks to return values that trigger the path
3. Setup mock interactions for exception scenarios

**Example with Mocking:**
```java
@Test
@DisplayName("Should handle database exception gracefully")
public void shouldReturnDefaultValue_WhenDatabaseThrowsExceptionTest() {
    // Arrange
    when(database.findApprover(anyString())).thenThrow(new SQLException("Connection failed"));
    
    // Act
    Approver result = myService.getApprover("id-123");
    
    // Assert
    assertNotNull(result);
    assertEquals("DEFAULT_APPROVER", result.getName());
    verify(database).findApprover("id-123");
}
```

#### Step 4: Add Test Methods to Test Class

1. Create new test methods in existing test class
2. Each method targets one uncovered code path
3. Follow naming convention: `shouldXxx_WhenYyyTest()`
4. Include `@DisplayName` annotation

#### Step 5: Compile and Run Tests

```bash
mvn clean compile
mvn clean test
```

Verify:
- Code compiles without errors
- All new tests pass
- No existing tests broken

#### Step 6: Regenerate Coverage Report

```bash
mvn clean package
```

Review updated JaCoCo report:
- Check coverage for previously low-coverage method
- Verify uncovered lines are now covered
- Compare old % vs new %

**Expected Results:**
- Previously uncovered lines now shown in green
- Method coverage percentage increased
- Target: >= 80% coverage achieved

#### Step 7: Verify Coverage Met 80% Threshold

If coverage still < 80%:
1. Identify remaining uncovered lines
2. Design additional test cases (repeat steps 1-6)
3. Continue until coverage >= 80%

If coverage >= 80%:
1. Document improvement (method name, old % → new %)
2. List new test methods added
3. Proceed to next method below 80%

# Pipeline Architecture — Java Upgrade Agent Suite

This document describes the internal architecture, data flow, and design decisions
of the Java upgrade agent pipeline.

---

## High-level pipeline

```
User types: @java-upgrade-orchestrator .
                        │
                        ▼
            ┌───────────────────────┐
            │   ORCHESTRATOR        │  Phase 0: Pre-flight
            │   (entry point)       │  Phase 1: Detect source from pom + target selection
            └──────────┬────────────┘
                       │
                       ▼
            ┌───────────────────────┐
            │   AUDIT AGENT         │  Phase 2: Deep codebase scan
            │   (read-only)         │  Returns: audit_results (JSON)
            └──────────┬────────────┘
                       │
                       ▼
            ┌───────────────────────┐
            │ REQUIRED CHANGES FILE │  Phase 2: Create .java-upgrade-required-changes.md
            │ (human-readable list) │  Before any apply step
            └──────────┬────────────┘
                       │
                       ▼
            ┌───────────────────────┐
            │   USER REVIEW GATE    │  Phase 2.5: See fix list, approve/exclude
            │   (dry-run mode)      │  Fixer runs in dry-run to generate plan
            └──────────┬────────────┘
                       │
                       ▼
            ┌───────────────────────┐
            │   FIXER AGENT         │  Phase 3: Apply approved fixes
            │   (password-gated)    │  Returns: APPLIED / PARTIAL / AUTH_FAILED
            └──────────┬────────────┘
                       │
                       ▼
            ┌───────────────────────┐
            │   VALIDATOR AGENT     │  Phase 4: Compile + JUnit + Diff + Charset + Risk + Security
            │   (read-only)         │  Returns: PASS / WARN / FAIL
            └──────────┬────────────┘
                       │
               ┌───────┴────────┐
               │                │
           PASS/WARN           FAIL
               │                │
               ▼                ▼
           ✅ Done      ┌──────────────────┐
                        │  User choice:    │
                        │  ROLLBACK        │──► ROLLBACK AGENT
                        │  MANUAL          │
                        │  RETRY           │──► Re-invoke FIXER
                        └──────────────────┘
```

## Mandatory Safety Gates (GHCP)

The orchestrator and fixer are now hardened to prevent silent code changes.

Apply mode is allowed only when all gates are passed in order:

1. Audit completes and findings are shown.
2. Required-changes report is generated and shown.
3. Fixer dry-run plan is shown (no file edits).
4. User approval is captured (ALL or reviewed subset).
5. User types `PROCEED`.
6. User echoes a one-time confirmation token.
7. Fixer requests authorization password in chat.

If any gate fails, the run aborts with no changes.

Additional guard:
- The fixer defaults to `dry-run` mode when `mode` is missing.
- `mode=apply` is blocked unless `apply_guard=APPROVED_BY_ORCHESTRATOR` is provided by the orchestrator.

## Version boundary system

The audit agent uses a **boundary gate** system to avoid running checks that don't
apply to the upgrade path. Every check is gated to one or more boundaries:

```
source_version = 8, target_version = 17

Active boundaries = { B9, B11, B15, B16, B17 }

B9  → source(8) < 9  AND target(17) >= 9  ✅ active
B11 → source(8) < 11 AND target(17) >= 11 ✅ active
B15 → source(8) < 15 AND target(17) >= 15 ✅ active
B16 → source(8) < 16 AND target(17) >= 16 ✅ active
B17 → source(8) < 17 AND target(17) >= 17 ✅ active
B18 → source(8) < 18 AND target(17) >= 18 ❌ not active (target < 18)
B21 → source(8) < 21 AND target(17) >= 21 ❌ not active (target < 21)
```

**Important:** All boundary comparisons use integer arithmetic, not string comparison.
`"9" > "17"` is true as a string — never compare versions as strings.

---

## Fix-id naming convention

Fix IDs assigned by the fixer follow a `{category}-{sequence}` pattern:

| Prefix | Category | Example |
|---|---|---|
| `compiler-` | Compiler source/target/release in pom.xml | `compiler-01`, `compiler-02` |
| `plugin-` | Maven plugin version updates | `plugin-01` |
| `dep-` | Dependency additions (removed JDK modules) | `dep-01`, `dep-02` |
| `api-` | Deprecated API pattern replacements in .java files | `api-01` |
| `osgi-` | OSGi/AEM bundle compatibility | `osgi-01`, `osgi-02` |
| `manual-` | Issues requiring manual action (not auto-fixed) | `manual-001` |

Fix IDs are stable within a run and referenced in:
- The dry-run plan (for user exclusion)
- The checkpoint file (for resume and rollback)
- The validator's diff review (for consistency checking)

## Multi-module Maven handling

For projects with a parent POM and submodules, the audit scans **all `pom.xml` files**:

```
project-root/
├── pom.xml              ← parent
├── core/
│   └── pom.xml          ← scanned
├── ui/
│   └── pom.xml          ← scanned
└── it.tests/
    └── pom.xml          ← scanned
```

Each submodule may have its own:
- `maven.compiler.source` / `maven.compiler.target` — all are updated by the fixer
- Plugin versions — checked individually
- Dependencies — checked for split-package conflicts across modules

The parent POM's `<dependencyManagement>` is checked for conflicting versions.

## Security design

### Authorization model

```
Orchestrator (Phase 3)
    │
    │  Requires user to type: PROCEED
    │  Then: 6-digit one-time confirmation token
    │
    ▼
Fixer Agent (Step 1)
    │
    │  Requires interactive password: tcs_agent
    │  (typed directly in GHCP chat — never from env vars)
    │
    ▼
Files modified
```

Two-layer gate:
1. Orchestrator: confirm intent (PROCEED + token)
2. Fixer: confirm identity (password)

### Checkpoint integrity

The checkpoint file is plain markdown. It does not include a cryptographic signature.

**Risk:** If the checkpoint is manually edited or tampered with, the fixer may skip
or re-apply wrong fixes. Treat the checkpoint as a trusted internal file — do not
commit it to version control or share it.

### Pattern matching safety

All source file pattern searches exclude:
- `//` line comments
- `/* */` block comments
- String literals

This prevents false positives (e.g. `javax.xml.bind` inside a Javadoc comment)
and prevents the fixer from editing comment lines.

```

           On FAIL → offer ROLLBACK / MANUAL / RETRY choice
```

### What the orchestrator asks you

At Phase 1, if you only provide project root, orchestrator reads pom.xml first,
detects current Java version, then presents valid target versions and asks you to choose.

- `ALL` — apply everything
- `compiler-01,api-01` — comma-separated fix-ids to **exclude** (those will be skipped; rest applied)
- `CANCEL` — abort, no files touched

At **Phase 3**, you'll be asked for the authorization password: `tcs_agent`


| 1 | Build config (compiler targets, enforcer, plugins) | Always |
| 2 | JVM startup flags (`--add-opens`, removed flags) | B9+ |
| 3 | Removed JDK modules (JAXB, JAX-WS, CORBA, etc.) | B11+ |
| 4 | Deprecated & removed API patterns | Per boundary |
| 5 | Reflection, encapsulation, internal JDK APIs | B9+, B23+ |
| 6 | OSGi bundle compatibility | AEM only |
| 7 | Split-package detection | B9+ |
| 8 | Removed JDK tools & build scripts | B9+, B11+ |
| 9 | Spring Boot version matrix | Spring Boot only |
| 10 | CI/CD & container configuration (GitHub Actions, Dockerfile) | Always |

### Output format

The audit emits:
1. A **human-readable report** with detailed findings (file + line + fix hint)
2. A **structured JSON object** (`audit_results`) passed to the orchestrator/fixer
3. A required changes artifact generated by orchestrator: `.java-upgrade-required-changes.md`

### Saving results to cache

When called via the orchestrator, results are saved to `.java-upgrade-audit-cache.md`
automatically. To save when running standalone, copy the output to a file.

## 🔧 Fixer — standalone apply

**File:** [`.github/agents/java-upgrade-fixer.agent.md`](../.github/agents/java-upgrade-fixer.agent.md)

> **Best practice:** Run the fixer via the orchestrator, not directly.
> The orchestrator provides the dry-run review gate, manual approval, and validator.

### What the fixer auto-fixes

| Category | Fix applied |
|---|---|
| Compiler targets | Updates `maven.compiler.source`, `maven.compiler.target`, `<release>` in all `pom.xml` files |
| Maven compiler plugin | Updates to `3.10.1` if below minimum |
| Removed JDK modules | Adds `jakarta.xml.bind-api`, JAX-WS RI dependencies to `pom.xml` |
| Deprecated API patterns | Replaces `new Integer(x)` → `Integer.valueOf(x)` (and Long, Double, Float, Boolean) |
| OSGi bundle (AEM) | Updates `maven-bundle-plugin` version, `Bundle-RequiredExecutionEnvironment` |

### What the fixer does NOT auto-fix (manual action required)

- `sun.misc.*` / `com.sun.*` imports — logic refactor needed
- Nashorn engine calls — choose replacement (GraalVM JS, Rhino)
- `--add-opens` / `--add-exports` startup flags — must be added to server scripts manually
- Library upgrades (Lombok, ASM, ByteBuddy) — test before upgrading
- Thread.stop() / Thread.suspend() — behavioral refactor needed
- CI/CD YAML hardcoded Java versions — detected but not modified

### Checkpoint & resume

The fixer writes a checkpoint after every individual fix. If it's interrupted:

```
.java-upgrade-fixer-checkpoint.md
```

Re-invoke the orchestrator with `--skip-audit` to resume from where it stopped —
already-applied fixes are skipped automatically.

### Dry-run mode

The orchestrator always runs the fixer in dry-run first (Phase 2.5) before apply.
You cannot skip this review gate.

## ✅ Validator — standalone validation

**File:** [`.github/agents/java-upgrade-validator.agent.md`](../.github/agents/java-upgrade-validator.agent.md)

### 6 checks performed

| Check | What | Pass condition |
|---|---|---|
| 1. Compile | `mvn clean compile -B` | Exit code 0 |
| 2. JUnit | `mvn test -B` — before/after comparison | No new failures vs baseline |

## ↩️ Rollback — undo applied fixes

**File:** [`.github/agents/java-upgrade-rollback.agent.md`](../.github/agents/java-upgrade-rollback.agent.md)

Rollback reads the fixer checkpoint and reverts every completed fix **in reverse order**.

### Dry-run first (recommended)

```
@java-upgrade-rollback . .java-upgrade-fixer-checkpoint.md --dry-run
```

This shows exactly what would be reverted — no files touched.

### Actual rollback

```
@java-upgrade-rollback . .java-upgrade-fixer-checkpoint.md
```

You'll be prompted for the authorization password: `tcs_agent`

### What it reverts

| Fix type | Rollback action |
|---|---|
| Compiler targets | Restores source/target to `source_version` |
| Dependencies added | Removes the added `<dependency>` block |
| API pattern replacements | Restores `Integer.valueOf(x)` → `new Integer(x)` |
| OSGi BREE | Restores `Bundle-RequiredExecutionEnvironment` |
| Plugin versions | ⚠️ WARN — original version not recorded; must revert manually |

After rollback, the checkpoint is renamed to `.java-upgrade-fixer-checkpoint.md.rolled-back`
(not deleted — kept for audit trail).

## Resume & recovery scenarios

### Scenario A — Audit completed, then session closed

```
@java-upgrade-orchestrator . java8 java17 --skip-audit .java-upgrade-audit-cache.md
```

The orchestrator loads the cached audit and skips straight to Phase 2.5 (review gate).
You can also review `.java-upgrade-required-changes.md` before resuming.

### Scenario B — Fixer stopped mid-run (partial changes)

The checkpoint records what was applied. Re-invoke the orchestrator:

```
@java-upgrade-orchestrator . java8 java17 --skip-audit .java-upgrade-audit-cache.md
```

The fixer reads the checkpoint, skips already-applied fixes, and resumes from where it stopped.

### Scenario C — Validator failed, want to start over cleanly

```
@java-upgrade-rollback . .java-upgrade-fixer-checkpoint.md
```

Then re-run the full pipeline after fixing the underlying issue.

### Scenario D — User excluded too many fixes and wants to re-apply some

Delete or rename the checkpoint file, then re-invoke the orchestrator with `--skip-audit`.
The fixer will re-run from scratch (without the exclusions).

## Tips & common mistakes

### ✅ Do this

- Always run `@java-upgrade-audit` first to understand the scope before applying fixes
- Use `--estimate-only` for large projects to get a quick count before committing time
- Review the proposed fix list at Phase 2.5 — exclude anything you want to handle yourself
- Add temp files to `.gitignore` before committing
- Run `mvn clean compile` manually after fixes even if the validator ran — sanity check

### ❌ Avoid this

| Mistake | Why it's a problem |
|---|---|
| Providing a non-existent `--skip-audit` cache file | Orchestrator starts a fresh audit (warns you) |
| Running on a Gradle project | Agents only support Maven — will exit with a clear message |
| Typing the password into the wrong prompt | Authorization fails; no files modified (safe) |
| Committing `.java-upgrade-fixer-checkpoint.md` | Leaks internal state; add to `.gitignore` |
| Running fixer without reviewing dry-run | The orchestrator prevents this — Phase 2.5 is mandatory |
| Assuming validator PASS means zero charset risk for Java < 18 | Charset check only runs when `target_version >= 18` |

|---|---|---|
| 🔴 | Critical | Will break compile or runtime — must fix before upgrade |
| 🟡 | Medium | Deprecated or risky — should fix; may work now but will break in a future version |
| 🟢 | Low / Safe | Informational — worth knowing but no action required |

# Java Breaking Changes Quick Reference

A concise developer reference for what breaks at each Java version boundary.
Use this alongside the audit report to understand **why** each finding is flagged
and what the correct fix is.

> **Coverage:** Java 8 → 26 | Boundaries: B9, B11, B15, B16, B17, B18, B21, B23, B24, B25, B26

---

## How to read this document

Each section covers one version boundary. A boundary `BN` is **active** when your
upgrade crosses it — i.e. `source_version < N` AND `target_version >= N`.

**Severity icons:**
- 🔴 **Critical** — breaks compile or runtime; must fix before upgrade
- 🟡 **Medium** — deprecated/risky; fix soon; may silently fail in a future version
- 🟢 **Low** — informational; worth knowing but no immediate action required

## B9 — Java 8 → 9

### Module System (JPMS) introduced

The JDK is now modular. Code on the classpath is wrapped in an "unnamed module"
which cannot access encapsulated JDK internals without explicit `--add-exports` or `--add-opens` flags.

**What breaks:**
- Direct imports of `sun.misc.*`, `sun.reflect.*`, `com.sun.*` → compile error without `--add-exports`
- `ClassLoader.getSystemClassLoader()` may no longer return a `URLClassLoader` — casts break at runtime
- `-Xbootclasspath` flag removed from JVM
- `-Djava.endorsed.dirs` / `lib/ext` Extension Mechanism removed

**Fix pattern:**
```bash
# Add to JVM startup args for each internal package used:
--add-exports java.base/sun.misc=ALL-UNNAMED
--add-opens java.base/java.lang=ALL-UNNAMED
```

---

### Removed JDK tools

| Tool | Removed | Replacement |
|---|---|---|
| `native2ascii` | Java 9 | Not needed — use UTF-8 `.properties` directly |
| `extcheck` | Java 9 | Not needed |
| `jhat` | Java 9 | `jcmd <pid> GC.heap_info` + VisualVM |
| `-agentlib:hprof` | Java 9 | `-XX:StartFlightRecording` (JFR) |

---

### `java.version` format change 🟡

```java
// Before Java 9 — format: "1.8.0_xxx"
"1.8".equals(System.getProperty("java.version"))  // ❌ breaks on Java 9+

// After Java 9 — format: "9", "17.0.1", etc.
Runtime.version().feature()  // ✅ correct way
```

---

### `_` single-character identifier 🔴

```java
int _ = 5;  // ❌ compile error in Java 9+ (was warning in Java 8)
```

## B11 — Java 9/10 → 11

### Removed JDK modules (JEP 320) 🔴

These packages were part of the JDK in Java 8 but are now completely removed:

| Package | Replacement dependency |
|---|---|
| `javax.xml.bind.*` (JAXB) | `jakarta.xml.bind:jakarta.xml.bind-api:3.0.1` |
| `javax.xml.ws.*` (JAX-WS) | `com.sun.xml.ws:jaxws-ri` |
| `javax.activation.*` | `jakarta.activation:jakarta.activation-api` |
| `javax.annotation.*` | `jakarta.annotation:jakarta.annotation-api` |
| `com.sun.xml.bind.*` | Standalone JAXB-RI |
| `com.sun.xml.ws.*` | JAX-WS RI |
| `org.omg.*` (CORBA) | No replacement — redesign required |
| `javax.transaction` | Jakarta Transactions standalone |

**pom.xml fix example:**
```xml
<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>3.0.1</version>
</dependency>
```

### Removed JDK tools (B11)

| Tool | Removed | Replacement |
|---|---|---|
| `javah` | Java 10 | `javac -h <dir>` |
| JavaDB (Apache Derby) | Java 11 | Use standalone Derby or H2 |

```bash
-XX:+PrintGC

-Xlog:gc*
-Xlog:gc:file=gc.log
```

### Nashorn JavaScript engine removed 🔴

```java
// ❌ broken — Nashorn engine gone
ScriptEngine engine = new ScriptEngineManager().getEngineByName("nashorn");

// ✅ alternatives:
// - GraalVM JS (via GraalVM distribution)
```

### RMI Activation removed 🔴

```java
// Redesign required — no direct replacement
```

### Primitive wrapper constructors — now Critical 🔴

```java
// 🔴 Critical if target >= 15 (deprecated since Java 9, forRemoval since 15)
new Integer(42)    // → Integer.valueOf(42)
new Long(42L)      // → Long.valueOf(42L)
```

## B16 — Java 15 → 16

### Strong encapsulation enforced 🔴

The `--illegal-access=permit` flag that silently allowed reflective access to JDK
internals is **removed**. All such access now throws `InaccessibleObjectException`.

```bash
# ❌ broken — flag is ignored (warns on Java 9-15, error on Java 16+)
--illegal-access=permit

# ✅ replace with explicit flags:
--add-opens java.base/java.lang=ALL-UNNAMED
--add-opens java.base/java.util=ALL-UNNAMED
```

## B17 — Java 16 → 17

### SecurityManager deprecated for removal 🟡

```java
// 🟡 Medium — still works but will throw unconditionally from Java 18+
System.setSecurityManager(myManager);   // deprecated forRemoval=true
System.getSecurityManager();            // deprecated forRemoval=true
```

### `java.lang.Compiler` removed 🔴

```java
// ❌ compile error — class completely removed
java.lang.Compiler.command(null);

// ✅ no replacement needed — JIT compiles automatically
```

### `sealed` keyword reserved 🔴

```java
// ❌ compile error — 'sealed' is now a keyword

// ✅

```

### AOT compiler (`jaotc`) removed 🔴

```bash
# ❌ tool removed from JDK 17

# ✅ alternative: GraalVM native-image (separate distribution)
```

## B18 — Java 17 → 18

### Default charset → UTF-8 (JEP 400) 🔴

This is the most impactful **silent** breaking change in the 8→21 upgrade path.
On Windows, the platform default charset was `Cp1252` (Windows-1252).
From Java 18+, **all platforms default to UTF-8**.

```java
// 🔴 SILENT DATA CORRUPTION on non-UTF-8 platforms:
new FileReader("data.txt")              // charset was Cp1252, now UTF-8
new FileWriter("out.txt")              // same
new InputStreamReader(stream)          // same
new OutputStreamWriter(stream)         // same
"hello".getBytes()                     // was Cp1252 bytes, now UTF-8 bytes
new String(bytes)                      // was Cp1252 decode, now UTF-8 decode

// ✅ explicit charset — correct for any Java version:
new FileReader("data.txt", StandardCharsets.UTF_8)
new FileWriter("out.txt", StandardCharsets.UTF_8)
new InputStreamReader(stream, StandardCharsets.UTF_8)
"hello".getBytes(StandardCharsets.UTF_8)
new String(bytes, StandardCharsets.UTF_8)
```

> ⚠️ This does NOT produce a compile error or test failure — only data corruption
> when reading/writing files on systems with a non-UTF-8 platform charset.

---

### `Charset.forName("default")` throws 🔴

```java
// ❌ throws UnsupportedCharsetException in Java 18+
Charset.forName("default")

// ✅
Charset.defaultCharset()   // returns UTF-8 from Java 18+
```

### `setSecurityManager(non-null)` throws 🔴

```java
// ❌ throws UnsupportedOperationException from Java 18+
System.setSecurityManager(new MySecurityManager());

// ✅ remove SecurityManager usage entirely
```

### `finalize()` deprecated for removal 🟡

```java
// 🟡 Medium — remove finalizers; use try-with-resources or Cleaner API
@Override
protected void finalize() throws Throwable { ... }  // deprecated forRemoval

// ✅ replacement:
java.lang.ref.Cleaner cleaner = Cleaner.create();
cleaner.register(this, () -> { /* cleanup */ });
```

## B21 — Java 17/18/19/20 → 21

### Thread lifecycle methods removed 🔴

```java
// ❌ all removed — use interrupt-based coordination instead
thread.stop();
thread.suspend();
thread.resume();
threadGroup.stop();
threadGroup.suspend();
threadGroup.resume();

// ✅ correct pattern:
// Use volatile boolean flag + thread.interrupt() + InterruptedException handling
```

---

### `Thread.countStackFrames()` removed (Java 22) 🔴

```java
// ❌ removed in Java 22 (flag if target >= 22)
thread.countStackFrames()

// ✅ use StackWalker:
StackWalker.getInstance().walk(s -> s.count())
```

---

### Virtual Thread implications 🟡

```java
// 🟡 synchronized blocks pin the carrier thread when used with virtual threads
synchronized (lock) {
    // I/O operations here will pin the carrier — latency risk
}

// ✅ use ReentrantLock instead for virtual-thread-compatible locking:
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try { /* I/O */ } finally { lock.unlock(); }
```

---

### `new java.net.URL(String)` deprecated 🟡

```java
// 🟡 deprecated — throws MalformedURLException unconditionally in future
new URL("https://example.com")

// ✅
URI.create("https://example.com").toURL()
```
